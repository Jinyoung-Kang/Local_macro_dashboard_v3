## 8. QA-131 비싼 계산 동시 실행 상한 (2026-10-18~19)

- 설계: 독립 설계안 3개(최소 변경·사용자 경험·운영)를 심사해 '최소 변경' 안을 뼈대로 정함 — 캐시를 놓친 계산만 공정
  세마포어(자동 = 코어 절반·최소 1, 대기 2초, 대기열 32)로 묶고 넘치면 429 + `Retry-After: 2`. 캐시 적중·health·로그인·
  DB 장애 경로는 상한 밖. 사용자가 계획·429·환경변수 `COMPUTE_MAX_CONCURRENT`·AWS 자동(=1)을 승인.
- 측정에서 재시작 직후 몰림에 429가 나와(계획의 재검토 조건) 사용자 승인으로 같은 키 묶기를 더함. 독립 검토 2명의 지적
  (따르는 요청 상한 없음, 앞선 계산 거절에 따르는 요청까지 429, 예외 인스턴스 전달)을 재현 테스트 → 수정으로 보완.
- 결과([측정](evidence/2026-10-18/compute-limit.md)): RATE 50에서 health 14/120 → 121/121, 로그인 18초 → 0.1초 안팎,
  5xx·시간 초과 110건 → 0. 재시작 직후 몰림 429는 9회 중 1회 5건. 남은 한계는 공격 중 자주 읽는 키의 429 4–8%.
- 확인하지 못한 것: AWS 실제 인스턴스의 코어 수(자동 상한이 1이 되는지)는 반영 뒤 기동 INFO 로그로 확인. auto·live_only에서
  계산이 수집을 기다리는 동안 자리를 쥐는 한계는 문서에만 적음(AWS는 store_only라 해당 없음).
