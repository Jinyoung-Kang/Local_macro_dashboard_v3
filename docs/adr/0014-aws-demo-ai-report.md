# 0014. AWS 데모의 AI 리포트 — 엔진 허용 목록 · 데모 공용 하루 한도

- 상태: 채택 (2026-10). ADR 0012의 "공개 데모에서는 유료 AI 키를 비움"과 ADR 0013의 "데모 열람은 AI 리포트 생성을 막음"을 바꿉니다.
- 지키는 방법:
  - `AiServiceAllowListTest`: 비면 지금과 같음, 목록 밖은 키가 있어도 `not_allowed`, 허용됐지만 키가 없으면 `no_key`,
    `auto`는 키가 있는 허용 엔진이 둘 이상일 때만, 모르는 ID·`auto`는 기동 실패(ID 모양이 아닌 값은 문구에 없음),
    목록 밖 엔진·못 쓰는 `auto`는 네트워크 없이 실패, 폴오버·번역기도 허용된 것만
  - `UsageServiceDemoPoolTest`: 방문자 공용 한도, DB에 쓰지 않음, 실패 되돌림, KST 0시에 새로 셈, 동시 요청
  - `AiReportFlowTest`: 데모 한도 소진 응답 모양(엔진 호출 없음)·실패 되돌림·엔진 목록의 `quota`
  - `SessionFilterTest`(데모 열람): `POST /api/ai/report`만 통과, 같은 경로의 다른 메서드·HEAD·`/api/ai/test`는 403
  - `ApiIntegrationTest`: 데모 열람의 AI 리포트 요청까지 사용자별 테이블에 아무것도 쓰지 않음
  - 화면: `lib/__tests__/aiEngines.test.ts`, `app/(dashboard)/__tests__/demoViewer.test.tsx`·`actions.test.tsx`

## 배경

"수집한 데이터로 AI 리포트 쓰기"는 이 대시보드의 주요 기능인데, AWS 공개 데모에서는 두 겹으로 막혀 있었습니다.

- 배포 설정이 AI 키를 모두 비웠습니다(ADR 0012). 공개 주소에서 유료 AI가 불릴 위험 때문이었습니다.
- 데모 열람은 읽기 전용이라 `POST /api/ai/report`가 403이었습니다(ADR 0013). 막지 않았다면 데모 사용자 번호(-1)로
  `usage_counters`(users FK)에 쓰다가 500이 났을 것입니다.

방문자가 리포트를 직접 만들어 보게 하려면, 운영자의 Anthropic 계정에서 나가는 비용을 묶어야 합니다.

- **엔진**: 키가 있는 엔진을 모두 열면 비용·호출 한도를 엔진마다 따로 따져야 합니다. 비용을 아는 엔진 하나
  (Claude Haiku 5.5, 리포트 1건 약 1센트 미만 — ADR 0007)면 상한을 계산할 수 있습니다.
- **횟수**: 데모 방문자는 계정이 없어 사용자별 하루 한도를 쓸 수 없습니다.

로컬 사용은 지금과 같아야 합니다(새 설정이 비면 아무것도 바뀌지 않음).

## 결정

1. **엔진 허용 목록 `AI_ENGINES`**(`dashboard.ai.engines`, 쉼표로 구분한 엔진 ID). 비면 제한이 없습니다(기본·로컬).
   - 모르는 ID나 `auto`가 있으면 백엔드가 기동하지 않습니다. 오류 문구에는 쓸 수 있는 값을 적고, ID 모양이 아닌 값
     (키를 잘못 넣은 경우 등)은 적지 않습니다.
   - 엔진은 **허용됐고 키도 있을 때만** `available`입니다. 못 쓰면 `unavailableReason`이 이유를 줍니다 —
     `not_allowed`(목록 밖, 키가 없어도 이쪽이 먼저)·`no_key`. `keys`(제공자별 키 유무)는 그대로 둡니다.
   - `auto`: 목록이 없으면 지금처럼 키가 하나라도 있을 때. 목록이 있으면 **키가 있는 허용 엔진이 둘 이상**일 때만입니다.
     허용 엔진이 하나뿐이면 `not_allowed`, 둘 이상인데 키가 모자라면 `no_key`.
   - `enabled`(AI 메뉴)는 키가 있는 허용 엔진이 하나라도 있을 때입니다.
   - 목록 밖 엔진이나 못 쓰는 `auto`(엔진 미지정 포함)를 부르면 **네트워크에 나가지 않고** 키 없음과 같은 실패 모양
     (`"이 배포에서는 쓸 수 없는 엔진입니다: …"`)으로 끝납니다. 연결 시험(`/api/ai/test`)도 같습니다.
   - 자동 탐색은 허용된 엔진만 순서대로 봅니다. 목록 밖 엔진은 경로에 적지 않습니다(키가 빠진 사고가 아니라 설정이라).
   - 번역기(응답이 한국어가 아닐 때)는 그 제공자의 엔진이 목록에 있을 때만 부릅니다. 예를 들어 Cerebras만 허용하면
     Cloudflare 번역기를 부르지 않고 원문을 그대로 보입니다. Haiku는 한국어로 바로 쓰고, 번역이 필요하면 Haiku 자신이 합니다.
2. **AWS 배포(`compose.aws.yml`)**: `ANTHROPIC_API_KEY`는 서버의 `.env`에서 받고(비면 AI 꺼짐), `AI_ENGINES=anthropic_haiku`로
   고정합니다. NVIDIA·Cerebras·Cloudflare 키는 계속 비웁니다.
3. **데모 열람의 쓰기 예외는 `POST /api/ai/report` 하나**입니다.
   - `SessionFilter.demoForbidden`이 정확히 이 메서드·경로만 통과시킵니다. 다른 쓰기·HEAD·`/api/ai/test`는 그대로
     403 `demo_read_only`입니다.
   - 등급 검사는 접근 정책 표 그대로입니다(이 경로는 유료, 데모 열람은 유료 등급).
   - 앞단 Caddy 공개 쪽도 GET 밖의 `/api/*` 가운데 이 경로 하나만 통과시켜야 합니다(Caddy 설정은 이 저장소 밖).
4. **데모 공용 하루 한도 `AI_DEMO_DAILY_LIMIT`**(`dashboard.ai.demo-daily-limit`, 기본 20).
   - 데모 방문자 **전체가 함께** 씁니다. 백엔드 메모리(`UsageService`)에서 세고, `usage_counters`에는 쓰지 않습니다.
   - 한국 날짜가 바뀌면(KST 0시) 새로 셉니다. 동시 요청은 한 객체의 잠금 안에서 세어 한도를 넘지 않습니다.
   - 엔진이 모두 실패하면 한 건을 되돌립니다(계정 한도와 같은 규칙).
   - 다 쓰면 계정 한도 소진과 같은 모양으로 답하고 엔진을 부르지 않습니다 — 200
     `{"status": false, "error": "데모의 오늘 AI 리포트 한도(N건)를 모두 썼습니다. 내일(KST 0시) 다시 시도해 주세요.", "quota": {"used": N, "limit": N, "shared": true}}`.
   - `GET /api/ai/engines`는 데모 열람에게만 `quota: {used, limit, shared: true}`를 붙입니다. 화면은 생성 버튼 옆에
     "데모 방문자 전체가 하루 N건을 함께 씁니다"를 적습니다.
5. **화면**: 못 쓰는 엔진은 목록에 남기되 막고 이유를 적습니다(`no_key` "키 없음", `not_allowed` "이 배포에서 사용 안 함").
   처음 고르는 엔진은 `auto`, 못 쓰면 쓸 수 있는 첫 엔진입니다(AWS는 Haiku). 데모 열람은 이 화면의 생성 버튼만 풀리고,
   알림·계정 같은 다른 쓰기는 그대로 막힙니다.

## 이유

- **허용 목록을 따로 둔 이유**: 키를 비우는 것만으로는 "이 배포에서 어떤 엔진을 쓸지"와 "키가 있는지"가 섞입니다.
  엔진 선택을 따로 고정하면 운영자가 다른 키를 넣어도 공개 데모에서 열리지 않고, 화면도 고장처럼 보이는 "키 없음" 대신
  "이 배포에서 사용 안 함"이라고 정확히 말할 수 있습니다.
- **모르는 ID면 기동을 멈추는 이유**: 오타 하나로 모든 엔진이 `not_allowed`가 되면 AI가 조용히 꺼집니다. 데모 열람 토큰
  (ADR 0013)과 같은 원칙입니다 — 설정 실수는 기동할 때 드러나게 합니다.
- **엔진이 하나면 `auto`를 끄는 이유**: 자동 탐색은 "여러 엔진 중 되는 것 찾기"입니다. 하나뿐이면 같은 엔진을 이름만 바꿔
  부르는 선택지가 됩니다. 막아 두고 그 엔진을 기본으로 고릅니다.
- **메모리 공용 한도를 고른 이유**
  - 데모 열람은 DB 행이 없는 합성 사용자입니다(ADR 0013). `usage_counters`(users FK)에 쓸 수 없고, 쓸 수 있게 만들면
    "데모 열람은 DB에 쓰지 않는다"가 깨집니다.
  - 방문자를 구별할 계정이 없으므로 한도는 "데모 전체"가 정직합니다. 비용 상한이 하루 N건 × 건당 비용으로 바로 계산됩니다.
  - 데모의 백엔드는 EC2 한 대·한 프로세스입니다(ADR 0012).
- **받아들인 대가**
  - 백엔드를 다시 띄우면 그날 쓴 양을 잊습니다. 같은 날 다시 띄울 때마다 최대 N건을 더 쓸 수 있습니다
    (평일 아침에 새로 띄우는 것은 날짜도 바뀌므로 손해가 없습니다).
  - 한 방문자가 그날 한도를 다 쓰면 다른 방문자는 다음 날까지 못 씁니다. 데모의 비용 상한을 먼저 두었습니다.
  - 백엔드를 여러 대로 늘리면 한도도 대수만큼 늘어납니다. 그때는 이 결정을 다시 봅니다.

## 대안과 버린 이유

- **데모용 `users` 행을 만들어 `usage_counters`로 세기**: ADR 0013의 합성 사용자(DB 행 없음)를 되돌립니다. 세션·감사 기록 같은
  다른 사용자별 테이블도 그 행으로 쓸 수 있게 되어, 막아야 할 쓰기가 다시 늘어납니다.
- **사용자 FK가 없는 새 테이블에 세기**: 재시작에도 남지만 스키마 파일·저장소 코드가 늘어납니다. 메모리의 대가(같은 날
  재시작마다 최대 N건)가 데모 비용으로는 작다고 봤습니다.
- **방문자 IP별 한도**: 회사·통신사 NAT로 여러 사람이 한 주소를 나눠 쓰고, 한도의 합이 방문자 수에 비례해 비용 상한이
  사라집니다.
- **키는 비워 두고 미리 만든 리포트만 보여 주기**: "수집한 데이터로 직접 만들어 본다"는 시연 목적에 맞지 않습니다.
- **앞단(Caddy)에서만 횟수 제한**: 앞단은 엔진이 실패했는지(되돌림) 모르고, 화면에 남은 건수를 알려 줄 수도 없습니다.

## 결과

- 새 설정: `dashboard.ai.engines`(`AI_ENGINES`), `dashboard.ai.demo-daily-limit`(`AI_DEMO_DAILY_LIMIT`). 배포 `.env`에
  `ANTHROPIC_API_KEY`·`AI_DEMO_DAILY_LIMIT`(이름은 `.env.aws.example`). 로컬 `docker-compose.yml`은 `AI_ENGINES`만 넘깁니다
  (기본 빈 값 — 데모 열람은 로컬에서 켜지지 않으므로 데모 한도는 배포 파일에만).
- 새 경로 없음. `GET /api/ai/engines`에 엔진별 `unavailableReason`, 데모 열람에게 `quota`. `POST /api/ai/report`의 `quota`에
  데모면 `shared: true`(계정 사용자의 응답 모양은 그대로).
- 저장소 밖에서 할 일
  - 앞단 Caddy 공개 쪽: GET 밖 `/api/*` 차단에서 `POST /api/ai/report` 하나를 뺍니다. 관리자 쪽은 그대로입니다.
  - 리포트 생성은 수 초~수십 초 걸립니다. 앞단(CloudFront·Caddy)의 응답 대기 한도가 이보다 짧으면 방문자는 오류를 받으므로,
    배포 때 그 설정을 확인합니다.
- 검증은 로컬 테스트까지입니다. AWS에서의 실제 Haiku 호출과 Caddy 규칙은 이 변경에서 확인하지 않았습니다.
