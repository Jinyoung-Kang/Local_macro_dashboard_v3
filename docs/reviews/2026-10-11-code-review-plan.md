## 0. 요약

- **S1은 없다.** 구조 규칙(ADR 0001 백엔드 계층, ADR 0004 화면 계층)은 실제로 지켜지고 있다.
  화면의 raw `fetch`는 `lib/api.ts` 한 곳뿐이고, 데이터를 가공하는 `useEffect`도 없다.
  그래서 **구조를 새로 짜지 않고**, 결함을 고치는 자리에서 떼어 낼 가치가 있는 것만 뗀다(3건).
- 가장 큰 위험은 **다시 받을 수 없는 저장 데이터의 오염**이다(수집기 S2 6건).
  - 기관 '5일 누적'으로 저장된 레이더 값이 실제로는 '당일' 값이다.
  - 토스 추정치가 그날의 실제 이력을 지운다.
  - 몇 시간 지난 국채 금리가 현재 값으로 찍힌다.
  - 13F 공시 하나만 실패해도 분기가 한 칸 밀린다.
  - 풋옵션이 롱 보유로 계산된다.
- 보안은 S2가 4건이다.
  - LAN에서 인증 없이 로그인 해시로 메모리를 고갈시킬 수 있다.
  - 데모 방문자가 큰 본문으로 백엔드 힙을 고갈시킬 수 있다.
  - 거절·빈 응답을 유도하면 데모 AI 비용 상한을 우회할 수 있다.
  - 수집기 로그에 FRED API 키가 남는다.
- **Next.js 15의 지원이 2026-10-21에 끝난다**(공식 정책: 메이저는 출시 후 2년, 15.0 = 2024-10-21).
  화면이 AWS에 공개돼 있어 이번에 16으로 옮긴다.
- 성능: 10-03 측정(동시 50명 p95 38ms) 뒤로 새 병목은 찾지 못했다. 성능을 노린 변경은 하지 않는다.
  성능에 영향이 갈 수 있는 변경(Next 16, 묶음 UPDATE)만 전후를 잰다(§7).

## 7. 진행 방식과 검증

- 브랜치 `claude/hardening-2026-10`. 순서: §1 보안 → §2 데이터 → U-1~U-7 → §3 → §4.
  화면 결함은 Next 16 위에서 고쳐 테스트가 새 런타임에서 돈다.
- **결함마다 커밋 두 개**: `test(QA-###)` 재현 테스트(수정 전 코드에서 실패 → `@Disabled`/xfail) → `fix(QA-###)` 근본 원인 수정.
  옮기는 커밋(`refactor`)과 고치는 커밋을 섞지 않는다. 테스트가 없는 코드를 옮길 때는 현재 동작 고정 테스트를 먼저 둔다.
- **모든 커밋이 `make test` 통과**(ruff·pytest / `mvn verify` / 자가검증·vitest·eslint·tsc·build). 백엔드는 CI와 같은 JDK 21로 확인.
- 단계마다 `main`에 fast-forward 병합 → GitHub push → CI 6개 job 확인.
- 성능 전후(QA 스택에서 측정, 운영 스택은 쓰지 않음):
  - Next 16: `next build` 시간, 클라이언트 JS 총량(gzip), `/macro` 첫 로드 전송량
  - 회귀 확인: API 16경로 `scripts/bench-api.sh`
  - QA-020: 읽음 처리 1,000건
- 화면 변경은 QA 스택을 브라우저로 띄워 바뀐 화면을 직접 확인한다(빌드 통과만으로 닫지 않음).
- 끝나기 전에 **별도 에이전트가 전체 diff를 처음 보는 리뷰어로 검토**한다. 정확성·요구사항 문제만 고친다.
